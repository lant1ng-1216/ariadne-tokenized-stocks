# BSC tokenized-stock purchase flow

This document describes the first constrained SDK/MCP purchase route: one explicitly selected bStocks representation on BSC, paid with the allowlisted USDT contract. It does not change Ariadne's broader research or future asset support.

## Supported sequence

1. Select exactly one asset representation on chain `56` and platform `bstock`. The caller must resolve multiple returned candidates explicitly; the purchase tools do not choose an issuer silently. Quote/action planning and approval construction also fail closed unless the provider returns exactly one route; no code silently selects the first route.
2. Resolve USDT from Ariadne's BSC allowlist and verify the chain, deployed contract, on-chain `symbol`, and `decimals` by read-only `eth_call`. Read the selected stock token's on-chain symbol and decimals too. Amount conversion uses those verified decimals.
3. A selected issuer and stock are not enough to create the browser purchase intent. Ask the user for the current USDT amount and never copy it from an earlier plan or test. Do not ask the user to paste a wallet address or choose slippage and network-fee values for each browser purchase. Check wallet-handoff relay readiness, resolve the exact BSC representation, record the market baseline when available, and return a wallet-free purchase-intent link. The product defaults are a 2% maximum slippage and the current provider-derived network-fee estimate. Opening the link is the first wallet action: the external page requests the user's current MetaMask account, confirms BSC, and only then obtains the wallet-bound Binance Web3 quote, allowance state, fee estimate and exact plan. The link itself contains no wallet transaction request. SDK and lower-level non-browser integrations continue to require an explicit wallet address and risk inputs. Unknown market status remains unknown; a separate provider `openState=true` signal is shown as a caveat and is not treated as proof the market is open. When the swap gas estimate cannot be verified before a missing allowance is granted, keep the purchase intent visible, prepare the separate exact allowance, then fetch a fresh quote and fee estimate after allowance finality. This allowance step is an authorization prerequisite, not a wallet-funds check.
4. Build the provider transaction with that exact slippage value. Require its `tx.minReceiveAmount` to be present and at least the locally calculated minimum. Display the exact input, expected and minimum output in token units, token identities/contracts, spender, transaction target, quote expiry, route fee estimate, gas estimate, and reviewed/proposed gas cap before confirmation. If observed route conditions exceed the user's current slippage limit, stop and show the new quote/impact and a proposed limit; the user can change the limit by button or natural language, but that requires a fresh quote, a new plan, a new simulation, and a new confirmation. Never silently widen the limit.
5. If allowance is insufficient, keep the requested purchase plan visible and route to a separate exact ERC-20 allowance step. `prepare_bsc_stock_allowance_approval` shows the USDT amount, verified token contract, spender, fee estimate, expiry and market caveat. It builds and simulates a separate `approve(spender, exactAmount)` call. A provider gas-limit estimate may fall back to gas fields returned by the exact approval builder; no balance is read to qualify the wallet for review. If the simulator reports only insufficient token/gas funds, show that as an unverified-funds warning and still allow the wallet page; do not claim the simulation passed. Other simulation failures still block. Ariadne does not check whether the wallet has enough USDT or gas before opening the wallet page; MetaMask decides whether it can process the request. After approval finality, re-read allowance and attempt a balance read for context. A balance-read error is reported but does not block the fresh quote-backed plan; settlement handoff captures its own pre-transaction balance snapshot. Require the allowance to match the reviewed amount, then obtain a fresh quote and swap plan. Insufficient balance does not hide that plan or prevent the user from reaching their wallet.
6. The portal sends the wallet-returned hash through its one-time relay. The MCP app verifies the sender, USDT contract, exact approval calldata, reviewed fee cap, successful receipt and BSC finality. It re-reads USDT balance and allowance, but only the allowance determines whether the separate permission step completed; the wallet determines whether funds are sufficient for a later purchase. The app shows the finalized approval result and fresh plan to the Agent when the host supports conversation messages. Until finality, no fresh swap plan is reported. The prior allowance confirmation does not confirm the swap. Simulate the fresh unchanged swap plan; the MCP host's confirmation form approves only that exact plan and never signs or broadcasts.
7. Only for a separately owner-authorized live-pilot operation, hand the exact unsigned transaction, reviewed fee policy and wallet address to the wallet-capable application. In SDK clients, `GuardedEvmExecutionService.sendWithWalletProvider()` uses an injected EIP-1193 provider: it requests account access, checks the active BSC chain and selected account, rechecks the ERC-20 allowance, captures token balances for later settlement proof, then calls `eth_sendTransaction`. It does not reject the handoff because of current token or native balances. The wallet owns the key, shows its native transaction confirmation, decides whether the request can be submitted, and returns a transaction hash; Ariadne never reads a key or broadcasts this wallet-sent transaction.
8. For MCP Apps-capable clients, `prepare_stock_purchase_wallet_request` opens the Agent-native purchase review panel after the swap plan is simulated and explicitly confirmed. The panel automatically calls app-only `create_external_stock_purchase_handoff`; the server rechecks the exact confirmed plan, ERC-20 allowance, reviewed gas cap and quote expiry, captures before-balances solely for settlement reconciliation, reserves one attempt, and returns a short-lived portal URL. It does not gate on current token or native balances. The panel asks the host to open that URL with `openLink`, then keeps polling the same handoff. The branded page displays the reviewed transaction and plan, waits through a brief Ariadne transition, calls the browser's EIP-1193 `eth_requestAccounts`, verifies the planned wallet and BSC chain, and calls `eth_sendTransaction` with the exact reviewed request. The user's wallet shows its own transaction confirmation and remains the signer and broadcaster. No fake click or computer-use automation is used. If the host cannot auto-open links, the panel shows a fallback link; if the browser rejects automatic wallet connection before the transaction request, the page shows a manual fallback. The portal returns the one-time wallet hash to the relay; app-only `reconcile_external_stock_purchase_handoff` verifies its exact transaction fields, BSC finality and before/after balances. The panel updates model context and uses MCP Apps `sendMessage` to trigger the Agent's detailed terminal report when that host capability is available. If the wallet call errors after it starts, its outcome is uncertain and the plan must not be resubmitted.
9. Poll the exact transaction and receipt on BSC and require its receipt block to be finalized before reading post-transaction balances. Wallet-submitted transactions must match the reviewed sender, target, value and calldata and stay within the reviewed gas ceiling; only a finalized successful receipt plus the exact input spend and minimum output delta is reported as success. Missing receipt, unverified finality, reverted, over-budget, or mismatched outcomes stay distinct. If the wallet provider times out after the user approves, do not resubmit the same plan; inspect wallet/chain state and use the reserved hash registration/reconciliation path.

The approval and purchase confirmations are separate. A fresh purchase plan must be simulated and confirmed after allowance verification. Approval planning estimates the approval transaction fee but does not read the wallet's BNB or USDT balance to decide whether to show the wallet page. If the provider simulation reports only that wallet funds or gas could not be verified, Ariadne shows that warning and leaves the affordability decision to the wallet. A reviewed maximum gas cap is a separate limit on the transaction itself; it is not a check of the wallet's available balance.

## SDK entry points

- `TokenizedStocksService.createBscStockPurchasePlan`
- `TokenizedStocksService.prepareBscStockAllowanceApproval`
- `TokenizedStocksService.refreshBscPurchaseAfterApproval`
- `GuardedEvmExecutionService.registerPrepared`, `simulate`, `confirm`, `sendWithWalletProvider`, `broadcastSigned`, and `reconcileBroadcast`

For SDK use, keep the same `GuardedEvmExecutionService` instance alive through reconciliation; its plan registry and pre-broadcast snapshot are process-local. The MCP server also holds its plan and before-balance snapshot in the current process, which must remain available until the result is terminal. The external portal solves the current Codex panel's custom sandbox-origin problem without asking the host to expose a wallet provider. The separate read-only connection check still accepts an injected provider or uses its WalletConnect fallback when configured. Local relay fixtures do not prove that a deployed HTTPS portal can auto-open MetaMask or that a specific Agent host can trigger a conversation report. The SDK accepts an injected EIP-1193 provider directly.

`eth_sendTransaction` wallet providers broadcast inside the wallet and return a hash. Ariadne therefore verifies transaction fields and the actual gas settings during reconciliation instead of inspecting signed bytes before the wallet sends. The request includes the reviewed gas fields and wallet-native confirmation is mandatory; if a wallet changes the transaction beyond the plan, Ariadne reports a mismatch and never calls it a reconciled purchase. Use the `broadcastSigned()` path when an integrator's wallet can return a signed raw transaction before broadcast, since that path validates it before Ariadne's guarded broadcaster.

## Current evidence boundary

## Wallet and provider responsibilities

Binance Web3 API is the data and transaction-construction/relay provider in this flow. Its API credentials authenticate Ariadne's requests; they are not the user's wallet and do not sign for the user's address. The Wallet API can read balances and transaction history. For a standard EVM `SWAP`, the user wallet signs the built transaction; an EIP-1193 wallet such as MetaMask can broadcast it directly, or Ariadne's Binance transaction relay can relay raw bytes only after a client wallet has signed them. For an `RFQ`, the user wallet signs the returned EIP-712 typed data, then Ariadne can submit that signed order to Binance Web3 and poll the vendor-relayed settlement. Ariadne should reuse Binance's quote, approve/build, gas, simulation, status, and relay APIs rather than reimplement their router/settlement providers.

The Binance Web3 API reference currently says equity/RWA routes always use `RFQ`; the bounded Live NVDAB probe recorded on 2026-10-05 returned `SWAP` from both quote/build. This provider-contract discrepancy is unresolved. The implementation binds the build mode to the quote mode and fails closed on a mismatch; the first guarded BSC EVM path only accepts a standard `SWAP`, while RFQ signing/submission remains a separate, incompletely verified path. Do not infer execution mode from the token brand, API page, or an older quote.

MetaMask is a BSC-compatible user-controlled wallet; the supplied address does not need to be moved to a Binance exchange wallet. MetaMask documents gas-included Dapp transactions on BNB Smart Chain and lists USDT as an eligible gas token, with Smart Transactions and Estimate balance changes enabled. This is a viable first option to investigate for the owner's zero-BNB wallet, but it is not yet integrated or verified with Binance-built bStocks approval and swap requests. MetaMask's separate “gasless swaps” feature only applies to MetaMask Swaps and must not be assumed to cover a Binance-quoted route. Ariadne must only select a USDT-paid gas path when the wallet confirms it is available for the exact request and the displayed total USDT debit stays within the user's cap. Otherwise stop before wallet submission; converting USDT to BNB on-chain itself needs gas and is not a bootstrap path for an empty-BNB wallet.

The owner described a 10 USDT pilot amount. Treat the requested swap amount and any explicit spend ceiling as separate user inputs. Show the fresh transaction fee estimate in the plan; do not infer a spending ceiling from a balance read or block plan creation because of current holdings. The wallet decides whether the submitted transaction can proceed.

The intended Agent experience is part of the product delivery flow and must not depend on computer-use automation or an external browser companion. Research and issuer comparison remain in the existing MCP App. The exact USDT allowance review is returned in the Agent's native conversation with a direct, one-time wallet-page link; the full `#handoffId.capability` fragment must be preserved so the external page can retrieve the reviewed request. This avoids relying on the current Codex host's MCP App `openLink` button for this step. The user's browser wallet remains the signer/broadcaster. On 2026-10-09 the owner verified that a fresh purchase link opened the external Edge page and the page actively produced the MetaMask purchase confirmation for the tested bStocks NVDAB plan. Plan creation now also attaches a compact background monitor which watches that same handoff, reconciles the exact returned hash, atomically claims one terminal report and uses the host message capability; accepted delivery is persisted to prevent duplicate reports after App reloads. This revised automatic-report path remains owner-host unverified until the next purchase. No LLM or MCP server receives a private key.

For the MCP browser journey, 2% is the documented product maximum and remains a hard bound for the exact plan formed after wallet connection. If a later fresh quote moves beyond that boundary, show the measured difference and pause for the user's decision; never silently widen it. SDK callers may supply a different explicit cap through the lower-level API. A previous confirmation never authorizes widening any bound.

The purchase intent carries the conversation language. Chinese requests open a Chinese external page; English requests open an English page. Labels, state changes, wallet instructions, errors and post-transaction actions follow that language.

The SDK accepts an injected EIP-1193 provider. The unrelated Binance B402 API supports HTTP 402/x402 payments for API/resource access and their on-chain settlement; it is not the aggregator flow for buying a bStocks security.

Deterministic tests cover token identity binding, amount precision, quote/slippage/minimum-output binding, approval and purchase gas-budget checks, the in-panel allowance review, the one-time external allowance and purchase handoffs, returned-hash binding, receipt verification, balance reconciliation, replay rejection, and pending/reverted/mismatch outcomes. They use fixtures and make no real wallet request or network broadcast. Loopback HTTP is permitted for local browser-extension testing only; deployed portal links still require stable HTTPS.

Historical note: the 2026-10-06 probe used a random empty address; its provider simulation returned `BEP20: transfer amount exceeds balance`. That observed failure is not evidence that a real user's funds are sufficient or insufficient, and it is no longer used to block a plan or wallet handoff. The current code treats a narrowly identified funds-only simulation failure as an explicit warning and leaves submission eligibility to the wallet; transaction-content, market, allowance and gas-cap checks remain separate. The live response conflicts with Binance's current Trading API documentation that equity/RWA routes always return RFQ; the implementation keeps this discrepancy visible and the RFQ path is not approved for this BSC standard-EVM phase. The earlier zero-address builder error `40465` remains a separate historical observation. No owner wallet was used in those 2026-10-06 probes. A later owner-authorized transaction is recorded below; that authorization applied only to that exact operation.
